# ArchiveLink (OTAC) connectivity runbook

How document-delivery reaches the OpenText Archive Center repository that S/4 archives into
(ADR [0009](../adr/0009-archivelink-source-typed-documents.md)). Discovery results are in
[endpoint-discovery.md](../endpoint-discovery.md#archivelink-repository-c1-otac).

## What the repository needs

`C1` **requires signed URLs**: an unsigned read answers `401 ICS:3003 … parameter secKey`. The
server verifies the signature against a certificate registered on the repository. It already
trusts RSA certificates, so we use an ordinary RSA key pair.

| Piece | Where | Owner |
|---|---|---|
| Cloud Connector mapping `otac-dev:8082` → `OTEMO.grupopuntacana.com:8082`, HTTP, path `/archive` and sub-paths | Cloud Connector | Basis |
| Destination `OpenText_OTAC` = `http://otac-dev:8082`, `OnPremise`, `NoAuthentication` | BTP cockpit | us (done) |
| Signing key pair + certificate | generated by us (below) | us |
| Certificate registered on `C1` with **read-only** permission and enabled | Archive Center administration | OpenText admin |
| Key pair in the Credential Store: `ArchiveLinkSigningKey` and `ArchiveLinkSigningCert` | BTP | us |

## 1. Generate the key pair

Generate it into `certs/`, which is git-ignored (the key is a secret; never commit it). Name the
files by landscape tier so DEV, QAS and PRD keys can't be mixed up:

```bash
mkdir -p certs
openssl req -x509 -newkey rsa:2048 -nodes -sha256 -days 3650 \
  -subj "/CN=BTP_DOCDELIVERY_DEV" \
  -keyout certs/archivelink-signing-dev.key -out certs/archivelink-signing-dev.crt
```

The certificate's `CN` becomes the `authId` (`CN=BTP_DOCDELIVERY_DEV`). Use one key pair per
landscape tier (DEV / QAS / PRD). To override the `authId`, set `ARCHIVELINK_AUTH_ID`.

## 2. Register the certificate on the repository

Send `certs/archivelink-signing-dev.crt` (public, safe to email) to the OpenText admin and ask them to:

1. Import it for logical archive **C1** with authId **`CN=BTP_DOCDELIVERY_DEV`**.
2. Grant **read only** (`r`). document-delivery never creates, updates or deletes.
3. **Enable** it (an imported certificate is inactive until enabled).

## 3. Verify with the probe

```bash
# in-office, direct
ARCHIVE_URL=http://OTEMO.grupopuntacana.com:8082 \
ARCH_DOC_ID=<a TOA01 ARC_DOC_ID> \
ARCHIVELINK_SIGNING_CERT_PATH=certs/archivelink-signing-dev.crt \
ARCHIVELINK_SIGNING_KEY_PATH=certs/archivelink-signing-dev.key \
OUT=/tmp/bill.pdf node scripts/probe-archivelink.js

# through the Cloud Connector (after Basis creates the mapping): same env, without ARCHIVE_URL
npx cds bind --exec --profile hybrid -- node scripts/probe-archivelink.js
```

| Step 4 result | Meaning |
|---|---|
| `200 · N bytes · application/pdf` | Done. |
| `401 · ICS:3001 … certificate … is unknown` | The signature is well-formed, but the certificate isn't registered or enabled on `C1` yet. |
| `401 · ICS:3009 … signature … is invalid` | The certificate is known but the signature doesn't verify: the key doesn't match the registered certificate, the clock is off, or something between us and the server rewrote the URL (the signature covers the values exactly as sent). |
| `401 · ICS:3003 … secKey` | No signer configured: set the certificate and key paths. |
| Step 1 fails | Connectivity: destination or Cloud Connector mapping. |

## 4. Store the key pair

Both halves go into the Credential Store, side by side. The certificate is public, but it and
the key are one pair: keeping them together means a rotation is one step in one place, and the
service picks it up within 10 minutes with no redeploy.

```bash
cf create-service-key credstore-shared cli
export CREDSTORE_CREDS="$(cf service-key credstore-shared cli | tail -n +2)"
node scripts/credstore-put.js key ArchiveLinkSigningKey  "$(cat certs/archivelink-signing-dev.key)"
node scripts/credstore-put.js key ArchiveLinkSigningCert "$(cat certs/archivelink-signing-dev.crt)"
cf delete-service-key credstore-shared cli
```

If the write fails with `certificate expired`, the `cli` service key is old: delete it and
create it again.

Then set `ARCHIVELINK_REPOSITORIES` in `secrets.mtaext` to the S/4 caller grant and deploy.

**Rotation:** generate a new pair, have the new certificate registered on the repository
*before* switching, then write both entries. Ask for the old certificate to be removed once
reads work with the new one.

The Destination service's certificate store is not the place for this pair. It holds keystores
a destination uses to authenticate the *connection* (TLS client certificates); the archive does
not authenticate the connection, it verifies a signature in each URL that our code produces.
